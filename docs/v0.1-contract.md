# v0.1 behavior and interface contract

This defines the implemented library/CLI behavior for [issue #1](https://github.com/Azhovan/rootfs-diff/issues/1), with concrete structs, validation and [schema examples](models.md). The separately tracked demonstration and delivery checks remain acceptance requirements; this contract does not claim their completion.

## Purpose and boundaries

Compare two complete rootfs tar archives and produce a deterministic review of their recorded contents and metadata. Deliver an importable Go library and a thin CLI. Linux and macOS are supported hosts; firmware CPU architecture is irrelevant because files are read, never executed.

The upstream repository is public. Cloning, installing and consuming its module do not require GitHub authentication. Optional private-copy/fork guidance covers authenticated module access without changing repository visibility.

Inputs: uncompressed tar and gzip-compressed tar, including ordinary USTAR, GNU, and per-file PAX long-name handling through Go's archive/tar. The scanner detects gzip by magic bytes, not filename. Both library inputs are io.Reader streams; CLI inputs are two local regular files. Standard input, URLs, archive extraction, raw flash images, SquashFS/ext4/cpio/OCI layers, and extracted-directory scanning are outside v0.1.

## Archive semantics

- Hash regular-file payloads with SHA-256 in bounded chunks. Retain metadata/hashes, not payloads. Memory may scale with entry count, not total payload bytes.
- Support regular files, directories, symlinks, hardlinks, character devices, block devices, and FIFOs. Device entries are metadata only. Never create host files from archive entries.
- Entry paths are POSIX root-relative strings such as `etc/device.conf`. Normalize repeated separators and `.` segments. Reject absolute paths, any `..` segment, invalid UTF-8, and duplicate normalized paths. Backslash is a literal POSIX filename character, not a separator. Ignore a root `.` directory entry; reject any non-directory root entry. A directory may be implicit, but an explicit non-directory ancestor of another entry is invalid. Manifests retain explicit entries only and never synthesize parent directories or invent their metadata. Adding/removing an explicit directory record is therefore a reported change even when descendants are unchanged.
- Compare numeric UID/GID, mode masked to 07777, entry kind, file size, content digest, link target, and device major/minor where applicable. Do not resolve user/group names against the host. Ignore timestamps, uname/gname, archive entry order, compression, directory sizes, and archive padding.
- Preserve valid UTF-8 symlink targets verbatim, including absolute targets and `..`; reject invalid UTF-8 targets. They describe the target device, not the host. Do not resolve symlinks or infer whether they are dangling.
- Canonicalize hardlink targets using the entry-path rules. Allow forward references and chains that end in a regular entry. Reject missing targets, cycles, and non-regular endpoints. A hardlink retains its kind and canonical target, and inherits its effective size, digest, mode, UID, and GID from the terminal regular entry. Ignore hardlink-header metadata because it cannot describe a distinct inode. Effective content changes are visible at every linked path; hardlink target changes remain visible separately.
- File sizes and counters use checked 64-bit arithmetic. Regular files may be empty. Non-regular payload bytes are unsupported and must fail clearly.
- Reject global PAX headers, sparse archives, unsupported entry types, malformed headers, truncated payloads, corrupt gzip checksums, and invalid links with actionable errors. Detect GNU sparse type and GNU/SCHILY sparse metadata before accepting an entry. Do not silently expand unsupported sparse content.
- Use archive/tar end-of-archive semantics, including an empty archive and EOF after a complete entry; do not add a custom requirement for two terminator blocks. Truncated headers/payloads still fail. After tar EOF, permit only zero decoded padding and finish reading through gzip EOF to validate checksums. Concatenated gzip members are allowed only when their combined decoded bytes form one valid tar stream plus zero padding; concatenated additional tar archives/nonzero trailing data fail. Counts/limits cover padding and metadata consumed while validating EOF.
- Xattrs, ACLs, file capabilities, SELinux labels, and unrecognized vendor PAX metadata are not compared. When encountered, emit stable `uncompared_metadata` warnings identifying path and metadata key, never the value. Metadata on an ignored root directory record uses warning path `.` without retaining a root entry; this exception applies only to warning paths. Reject invalid UTF-8 metadata keys so reporting cannot silently replace bytes. Standard PAX path/linkpath/size/uid/gid and deliberately ignored time/name fields are not warnings. Sparse metadata is an error, not a warning. Every report also declares the standard metadata exclusions so no-diff is not presented as full firmware equivalence.
- The scanner must not depend on GODEBUG or host path behavior to enforce these rules. Return no successful partial manifest on failure.

Default scan limits: 100,000 logical entries, 8 GiB decoded archive bytes including headers/padding, 2 GiB per regular-file payload, and 4,096 bytes per entry path or link target. Zero-valued Go options mean defaults; negative or otherwise invalid values fail. Caller/CLI overrides must be positive and validated. Wrap all decoded reads with the archive-byte budget, including metadata extensions. Check final decoded path/target lengths when archive/tar returns a header; use its bounded extension handling rather than writing a custom PAX parser. Hash payloads in bounded reads; check context cancellation between reads. Cancellation cannot interrupt an arbitrary reader already blocked inside Read, which must be documented.

## Library boundary

Module: `github.com/Azhovan/rootfs-diff`. Public root package: `rootfsdiff`. The repository pins Go 1.27.4 in `.go-version` and the `go.mod` toolchain directive, with module minimum Go 1.27.0. See [contributor setup](../CONTRIBUTING.md). Runtime code should need only the standard library.

Public entry points:

```go
Scan(ctx context.Context, r io.Reader, opts ScanOptions) (Manifest, error)
Compare(before, after Manifest, opts CompareOptions) (Diff, error)
ParsePolicy(r io.Reader) (Policy, error)
Evaluate(after Manifest, diff Diff, policy Policy) ([]Violation, error)
```

Export model types for Entry, Manifest, Change, Diff, Policy, Violation, Warning, and Report. A separate public `report` package imports the root package and exposes `Write(io.Writer, rootfsdiff.Report, Format) error` for text, JSON, and Markdown. Core never imports report. CLI code lives in `internal/cli` with an injectable Run function and thin `cmd/rootfs-diff/main.go`.

The library defines concrete structs, JSON tags, typed error categories, validation for caller-built manifests, and executable public examples for the models and scan/compare/policy/report operations. Consumers can distinguish invalid/unsupported input and limit failures with errors.Is/errors.As; preserve underlying I/O errors. Functions do not mutate inputs, print, exit, or access global mutable state.

Concrete model choices are specified in [Models and JSON schema version 1](models.md), [the structural JSON schema](report-v1.schema.json), and root package Go documentation. Caller-built manifests accept arbitrary entry/warning order; produced manifests and report collections are deterministic and sorted. Validation rejects duplicate paths, invalid field applicability, invalid hardlink closure/effective data and checked-total overflow without mutating inputs. All empty model arrays marshal as `[]`; absent change sides are explicit `null`. JSON modes are decimal integers for the `07777` mask, while human modes are octal. `Policy.MaxTotalGrowthBytes` is a pointer to distinguish omitted from zero. Schema version 1 and the complete report example define the shared renderer/policy fields.

## Comparison and growth

- Entries and changes sort lexicographically by canonical path. Added/removed entries carry the full applicable side. Modified entries carry before, after, and every changed field, in fixed order: kind, mode, uid, gid, size, sha256, link_target, device_major, device_minor. A type change is one modified record, not a remove/add pair.
- Ignore rules are exact canonical paths and directory prefixes only. Prefix `var/log` matches itself and `var/log/...`, never `var/logger`. Reject malformed paths; no glob, regex, or negation language. Apply the same rules to both sides before reporting changes and calculating totals. Warnings are never hidden by ignore rules.
- Total payload bytes are the sum of retained regular-entry sizes only; hardlink aliases, directories, links, devices, and FIFOs contribute zero. This is uncompressed regular payload size, not flash size or filesystem disk usage.
- Signed net growth = after total minus before total, including additions/removals and ignores. Positive-growth listings include added regular files and positive size deltas for paths regular on both sides, sorted by descending bytes then path; type transitions contribute the new regular payload or remove the old regular payload. Hardlink aliases never count again. Changing which path stores the regular payload versus a hardlink can produce topology and growth-list changes even when contents and net growth are unchanged; inode canonicalization is outside scope. Expose full changes in JSON and at most ten growth entries in human reports.
- No timestamps, absolute host filenames, or run-dependent fields in report output. Running on the same logical inputs/options produces byte-identical output. Empty arrays serialize as arrays, not null.

## Policies

One strict JSON policy file with `schema_version: 1`, `required_paths` (array of exact canonical paths), and optional `max_total_growth_bytes` (nonnegative integer; omitted means disabled, zero means no positive growth allowed). Reject unknown fields, duplicate JSON object keys, bad types, unsupported versions, trailing JSON, malformed paths, negative limits, and overflowing integers. Limit policy input to 1 MiB.

Required-path checks inspect the complete candidate manifest, even when the path is ignored in the comparison. Only explicit candidate entries count as present; an implicit parent directory does not satisfy a required path. Presence is sufficient; this rule does not follow symlinks or check a path's runtime usability. Growth policy evaluates net growth after ignore filtering. Equality with the limit passes; shrinking passes. Sort violations by rule then path. There are no inferred security rules, percentage budgets, arbitrary expressions, or policy auto-remediation.

Example:

```json
{
  "schema_version": 1,
  "required_paths": ["etc/init.d/S40network", "usr/bin/device-agent"],
  "max_total_growth_bytes": 1048576
}
```

## CLI and reports

```text
rootfs-diff [flags] BEFORE.tar[.gz] AFTER.tar[.gz]
  --format text|json|markdown   default text
  --policy FILE                optional strict JSON policy
  --ignore-path PATH           repeatable exact path
  --ignore-prefix PATH         repeatable directory prefix
  --fail-on-change             fail for any non-ignored change
  --max-entries N
  --max-archive-bytes N
  --max-file-bytes N
  --max-path-bytes N
  --help
  --version
```

Flags precede the two positional paths. Limits are decimal integers in bytes/counts. Shell redirection selects an output file; no output-file flag in v0.1.

Exit 0: comparison succeeded and enabled checks passed, including ordinary differences without a gate. Exit 1: policy violation or explicit fail-on-change. Exit 2: invalid arguments/policy, unsupported/corrupt input, limits, I/O/render failure, or cancellation. Help/version return 0 without input files. Policy failures still emit a complete report.

Stdout contains only the requested report; stderr contains operational diagnostics. Parse/scan/compare errors produce no report bytes. A downstream writer failure may leave partial output, returns 2, and must be documented. Do not buffer archive payloads to achieve output atomicity. Do not print progress to stdout.

JSON uses schema_version 1 and includes summary, changes, violations, warnings, and metadata exclusions. Before/after fields for an absent side are explicit null. Record warnings with a before/after source tag. Foundation fixes the full schema and representative golden examples before report/policy implementation.

Text/Markdown summarize counts, payload totals/growth, changes, policy failures, and warnings. Never truncate the changes themselves without an explicit indication; v0.1 renders all changes. Escape control characters, terminal escape sequences, Markdown metacharacters, and HTML in untrusted paths/targets. Render mode values in octal in human output and document their JSON representation.

## Required proof and user docs

Every implementation issue owns relevant unit tests. Cross-component acceptance uses independent expected fixtures, actual subprocess exit codes, and compiled public Go examples. Fast verification requires no network after Go setup, no root, hardware, Docker, or host tar implementation. Use Go fixture writers for metadata fidelity.

Ship a small deterministic synthetic demo and a separately runnable pinned Buildroot recipe comparing two generated rootfs tar archives with controlled removal, mode, content/size, and symlink changes. Buildroot proof must actually run on Linux or a local Linux container/VM before its issue closes. Save the pinned configuration, recipe, SHA-256 inputs, exact command, expected findings, and observed report in one example README; keep large images/build trees out of Git. Do not claim a real firmware validation based on synthetic fixtures.

User documentation must cover public installation/module consumption and optional private-copy authentication, CLI and public Go examples, supported inputs/hosts, path and link rules, every compared/excluded field, resource limits, errors, policy/ignore interactions, output schema/versioning, exit codes, CI use, troubleshooting, and how to reproduce both demos. No runtime correctness, bootability, OTA compatibility, CVE applicability, regulatory compliance, or complete security verdict is implied.
