# v0.1 behavior and interface contract

This contract defines the required library and CLI behavior for
[issue #1](https://github.com/Azhovan/rootfs-diff/issues/1). The [model
reference](models.md) describes the concrete structs, validation rules and JSON
examples. Demonstration and delivery checks are tracked separately in the
issues; describing a requirement here does not establish that it has passed.

## Purpose and boundaries

rootfs-diff compares two complete root filesystem (rootfs) tar archives and
reports changes in their recorded contents and metadata. It provides an
importable Go library and a CLI that calls the library. Reports must be
deterministic: the same logical inputs and options produce the same output
bytes. Linux and macOS are supported hosts. The firmware's CPU architecture does
not matter because archive contents are read, never executed.

The upstream repository is public. Cloning it, installing the CLI and using the
Go module do not require GitHub authentication. Optional guidance for private
copies and forks explains authenticated module access; it does not require
changing repository visibility.

Supported inputs are uncompressed tar and gzip-compressed tar, including
ordinary USTAR, GNU and per-file PAX long-name records handled by Go's
`archive/tar`. The scanner recognizes gzip from the input bytes, regardless of
the filename. The library reads each archive from a caller-supplied `io.Reader`
without opening files or fetching URLs itself. The CLI takes two local regular
files and does not accept standard input or URLs. v0.1 does not support archive
extraction, raw flash images, SquashFS, ext4, cpio, OCI layers or scanning
extracted directories.

## Archive semantics

The scanner must hash regular-file contents with SHA-256 in bounded chunks and
retain only metadata and hashes. Memory use may grow with the number of entries,
but must not grow with the total number of payload bytes. File sizes, counters
and totals use 64-bit arithmetic with overflow checks. Empty regular files are
valid; payload bytes on non-regular entries must produce a clear error.

Supported entry kinds are regular files, directories, symlinks, hardlinks,
character devices, block devices and FIFOs. Device entries describe metadata
only. The scanner must never create host files from archive entries.

Entry paths are POSIX paths relative to the archived filesystem root, such as
`etc/device.conf`. The scanner must remove repeated separators and `.` segments
to produce canonical paths. It must reject absolute paths, any `..` segment,
invalid UTF-8 and duplicate canonical paths. Backslash is a literal filename
character, not a separator. These rules must be enforced independently of
`GODEBUG` and host path behavior.

A root `.` directory record is ignored; a non-directory root record is invalid.
A parent directory may be absent from the archive, but an explicitly recorded
parent must be a directory. Manifests retain only explicitly recorded entries.
They must not invent parent directory records or metadata. Adding or removing
an explicit directory record is therefore a change, even if its descendants are
unchanged.

Comparison includes numeric UID/GID, mode bits masked to `07777`, entry kind,
file size, content digest, link target and device major/minor where applicable.
User and group names must not be resolved against the host. Timestamps,
`uname`/`gname`, entry order, compression, directory sizes and archive padding
are ignored.

Symlink targets must be valid UTF-8 and preserved exactly as recorded, including
absolute targets and `..`. They describe paths on the target device. The scanner
must not resolve symlinks or determine whether their targets exist.

Hardlink targets use the entry-path normalization rules. Forward references and
chains are valid if they end at a regular file. Missing targets, cycles and
chains ending at a non-regular entry must be rejected. A hardlink keeps its kind
and canonical target, but inherits effective size, digest, mode, UID and GID from
the regular file at the end of the chain. Hardlink-header metadata is ignored
because a hardlink cannot describe a separate inode. Changes to effective file
contents must appear at every linked path; target changes must also be reported.

Global PAX headers, sparse archives, unsupported entry types, malformed headers,
truncated payloads, corrupt gzip checksums and invalid links must produce
actionable errors. The scanner must detect GNU sparse entries and GNU/SCHILY
sparse metadata before accepting an entry, without silently expanding sparse
content.

The scanner follows `archive/tar` end-of-archive behavior. Empty archives and EOF
after a complete entry are valid; two terminator blocks are not required.
Truncated headers and payloads remain invalid. After tar EOF, only zero decoded
padding is allowed. Gzip input must be read through EOF to validate its checksum.
Concatenated gzip members are valid only if their combined decoded contents
form one valid tar stream followed by zero padding. A second tar archive or
nonzero trailing data must fail. Counts and limits include metadata and padding
consumed while validating the end of the input.

Extended attributes (xattrs), access control lists (ACLs), file capabilities,
SELinux labels and unrecognized vendor PAX metadata are excluded from comparison.
When encountered, they must produce stable `uncompared_metadata` warnings with
the path and metadata key, never the value. Warnings about an ignored root
directory record use path `.` without adding a root manifest entry. This path
exception applies only to warnings. Invalid UTF-8 metadata keys must be rejected
rather than silently replacing their bytes in a report.

Standard PAX `path`, `linkpath`, `size`, `uid` and `gid` fields, and deliberately
ignored time/name fields, do not produce warnings. Sparse metadata must produce
an error. Every report must declare the standard metadata exclusions so that a
report with no changes does not imply full firmware equivalence. A scan failure
must not return a successful partial manifest.

The default scan limits are 100,000 logical entries, 8 GiB of decoded archive
bytes including headers and padding, 2 GiB per regular-file payload, and 4,096
bytes per entry path or link target. Zero-valued Go options select defaults;
negative or otherwise invalid values must fail. Overrides must be positive and
validated. The archive-byte limit must cover all decoded reads, including
metadata extensions. When `archive/tar` returns a header, the scanner must check
the decoded path and target lengths. It must use the package's bounded extension
handling rather than a custom PAX parser.

The scanner must check context cancellation between bounded payload reads.
Cancellation cannot interrupt an arbitrary reader already blocked inside
`Read`; user documentation must explain this limitation.

## Library boundary

The module path is `github.com/Azhovan/rootfs-diff` and the public root package
is `rootfsdiff`. The repository pins Go 1.27.4 in `.go-version` and the `go.mod`
toolchain directive, with a module minimum of Go 1.27.0. See [contributor
setup](../CONTRIBUTING.md). Runtime code should use only the standard library.

Public entry points:

```go
Scan(ctx context.Context, r io.Reader, opts ScanOptions) (Manifest, error)
Compare(before, after Manifest, opts CompareOptions) (Diff, error)
ParsePolicy(r io.Reader) (Policy, error)
Evaluate(after Manifest, diff Diff, policy Policy) ([]Violation, error)
```

The library must export `Entry`, `Manifest`, `Change`, `Diff`, `Policy`,
`Violation`, `Warning` and `Report`. A separate public `report` package imports
the root package and provides `Write(io.Writer, rootfsdiff.Report, Format) error`
for text, JSON and Markdown. The root package must not import `report`. CLI code
lives in `internal/cli`, with an injectable `Run` function called by
`cmd/rootfs-diff/main.go`.

The library must define concrete structs, JSON tags, typed error categories and
validation for caller-built manifests. Executable public examples must cover
the models, scanning, comparison, policies and reporting. Consumers must be able
to distinguish invalid input, unsupported input and limit failures using
`errors.Is` and `errors.As`. Returned errors must preserve underlying I/O errors.
Functions must not modify inputs, print, exit or access mutable global state.

Model details are specified in [Models and JSON schema version 1](models.md),
the [JSON schema](report-v1.schema.json) and root package Go documentation.
Caller-built manifests may list entries and warnings in any order. Produced
manifests and report collections must be sorted and deterministic. Validation
must reject duplicate paths, fields that do not apply to an entry's kind,
invalid hardlink chains or effective metadata, and overflowing totals, without
changing the input.

Empty model arrays must encode as `[]`; absent change sides must be explicit
`null`. JSON modes are decimal integers representing the `07777` mask, while
text and Markdown use octal. `Policy.MaxTotalGrowthBytes` is a pointer so that
an omitted limit differs from zero. Schema version 1 and the complete report
example define the fields shared by rendering and policy evaluation.

## Comparison and growth

Entries and changes are sorted lexicographically by canonical path. Added and
removed records contain the complete entry on the applicable side. Modified
records contain both sides and every changed field, in this order: `kind`,
`mode`, `uid`, `gid`, `size`, `sha256`, `link_target`, `device_major`,
`device_minor`. A change in entry kind is one modification, rather than a removal
followed by an addition.

Ignore rules support only exact canonical paths and directory prefixes. The
prefix `var/log` matches itself and `var/log/...`, but not `var/logger`.
Malformed paths must be rejected. There is no glob, regular-expression or
negation syntax. The same rules apply to both sides before detecting changes
and calculating totals. Ignore rules must not hide warnings.

Total payload bytes are the sum of regular-file sizes after ignores. Hardlink
aliases, directories, symlinks, devices and FIFOs contribute zero. This measures
uncompressed file contents, rather than flash size or filesystem disk usage.
Signed net growth is the candidate total minus the baseline total, including
additions and removals.

The positive-growth list includes added regular files and positive size changes
for paths that are regular files on both sides. Changing an entry to a regular
file contributes its new payload; changing away from regular removes its old
payload from the total. Growth records are sorted by descending bytes, then
path. Hardlinks never count the same contents again. Swapping which path stores
the regular payload and which is a hardlink can change link structure and the
growth list while contents and net growth stay unchanged. Rewriting hardlink
groups to choose a common representative path is outside scope. JSON includes
all changes; text and Markdown show at most ten growth entries.

Report output must not include timestamps, absolute host filenames or values
that vary between runs. The same logical inputs and options must produce
byte-identical output. Empty arrays must encode as arrays, not `null`.

## Policies

The CLI accepts one strict JSON policy file, limited to 1 MiB. It must contain
`schema_version: 1` and `required_paths`, an array of exact canonical paths. The
optional `max_total_growth_bytes` is a nonnegative integer. Omitting it disables
the growth check; zero forbids positive net growth. The parser must reject
unknown fields, duplicate object keys, incorrect types, unsupported versions,
trailing JSON, malformed paths, negative limits and overflowing integers.

Required-path checks inspect the complete candidate manifest, including paths
ignored in the comparison. Only explicitly recorded candidate entries count as
present. An implied parent directory does not satisfy a required path. Presence
is sufficient: the check does not follow symlinks or determine whether a path
is usable at runtime. The growth check uses net growth after ignores; equality
with the limit and shrinking both pass. Violations must be sorted by rule, then
path. Policies do not infer security rules or support percentage budgets,
arbitrary expressions or automatic remediation.

Example:

```json
{
  "schema_version": 1,
  "required_paths": ["etc/init.d/S40network", "usr/bin/device-agent"],
  "max_total_growth_bytes": 1048576
}
```

## CLI and reports

```text
rootfs-diff [flags] BEFORE.tar[.gz] AFTER.tar[.gz]
  --format text|json|markdown   default text
  --policy FILE                optional strict JSON policy
  --ignore-path PATH           repeatable exact path
  --ignore-prefix PATH         repeatable directory prefix
  --fail-on-change             fail for any non-ignored change
  --max-entries N
  --max-archive-bytes N
  --max-file-bytes N
  --max-path-bytes N
  --help
  --version
```

Flags must precede the two positional paths. Limits are decimal integers
expressing bytes or counts. Use shell redirection to save a report; v0.1 has no
output-file flag.

Exit codes have these meanings:

- **0:** Comparison succeeded and all enabled checks passed. Ordinary
  differences pass when no check requires failure.
- **1:** A policy was violated, or changes were found with `--fail-on-change`.
  The command still produces a complete report.
- **2:** Invalid arguments or policy, unsupported or corrupt input, an exceeded
  limit, an I/O or rendering failure, or cancellation.

Help and version return 0 without requiring input files.

Stdout contains only the requested report; stderr contains operational
diagnostics. Parsing, scanning and comparison errors produce no report bytes.
A writer failure may leave partial output and returns 2; user documentation
must explain this. Archive payloads must not be buffered to make output atomic,
and progress messages must not be printed to stdout.

JSON uses `schema_version: 1` and includes the summary, changes, violations,
warnings and metadata exclusions. An absent `before` or `after` side must be
explicitly `null`. Warnings must identify their `before` or `after` source. The
foundation work establishes the full schema and representative expected-output
examples before rendering and policy implementation depend on them.

Text and Markdown summarize counts, payload totals, growth, changes, policy
failures and warnings. v0.1 must render every change. Both formats must escape
control characters and terminal escape sequences in archive paths and targets.
Markdown must also escape Markdown syntax and HTML. Text and Markdown must show
modes in octal; documentation must also explain their decimal JSON representation.

## Required proof and user docs

Each implementation issue must include relevant unit tests. Cross-component
checks use independently written expected fixtures, actual subprocess exit codes
and compiled public Go examples. After Go setup, fast verification must work
without network access, root, hardware, Docker or a host tar executable. Test
archives must be written with Go fixture helpers to preserve exact metadata.

The repository must include a small deterministic synthetic demo and a separate
Buildroot recipe pinned to specific inputs. The Buildroot example must compare
two generated rootfs tar archives with controlled changes to removal, mode,
contents, size and symlink targets. It must actually run on Linux or in a local
Linux container or VM before its issue closes. Its README must record the
pinned configuration, recipe, input SHA-256 hashes, exact command, expected
findings and observed report. Large images and build trees must stay out of Git.
Synthetic fixtures alone do not establish validation against real firmware.

User documentation must cover installation and Go module use, optional
authentication for private copies, CLI and public Go examples, supported inputs
and hosts, path and link rules, all compared and excluded fields, resource
limits, errors, policy and ignore interactions, output schema and versioning,
exit codes, CI use, troubleshooting, and reproduction of both demos. Reports
must not imply runtime correctness, bootability, OTA compatibility, CVE
applicability, regulatory compliance or a complete security verdict.
